# تشخیص و رفع مشکل: کدهای ناقص و اجرانشدن CSS/JS

**نسخه معیوب:** ۳.۰.۰ — **نسخه اصلاح‌شده:** `custom-html-snippets-3.0.1.zip`
**تست‌ها:** ۱۱۷ واحد + ۱۲ یکپارچه + ۲۲ رگرسیون = **۱۵۱ موفق، ۰ ناموفق**

مشکلی که گزارش کردید واقعی بود و من آن را بازتولید کردم. اشتباه از من بود — در نسخه ۳ یک تصمیم معماری غلط گرفتم که باعث تخریب داده می‌شد. پایین دقیقاً توضیح می‌دهم چه شد.

---

## چرا کدها ناقص ثبت می‌شدند؟

### علت ریشه‌ای: `sanitize_callback` در `register_post_meta`

در نسخه ۳ برای «پاک‌سازی متمرکز» این کد را نوشتم:

```php
register_post_meta( POST_TYPE, $key, array(
    'sanitize_callback' => function ( $value ) use ( $args ) {
        return Sanitizer::apply( $args['sanitize'], $value );
    },
) );
```

این کار **دو فاجعه** ساخت:

#### ۱. کد JavaScript از وسط بریده می‌شد

فیلد `_chs_js` قانون `raw_html` داشت که برای کاربران بدون `unfiltered_html` مقدار را از `wp_kses_post` می‌گذراند. اما `wp_kses_post` یک فیلتر **HTML** است و عملگرهای `<` و `>` را تگ می‌پندارد:

```
ورودی : for (var i=0; i<10; i++) { if (a<b && c>d) total++; }
خروجی : for (var i=0; i
        ↑ ۵۳ کاراکتر → ۱۵ کاراکتر
```

هر کد JS که `<`، `>`، `=>` (arrow function) یا `$("<div>")` داشت از همان نقطه قیچی می‌شد. این دقیقاً همان «کدهای ناقص» است که دیدید.

#### ۲. کد PHP کاملاً خالی می‌شد

قانون `raw_php` این بود:

```php
if ( ! Security::can_edit_php() ) {
    return '';   // ← کد را نابود می‌کرد
}
```

`can_edit_php()` به `current_user_can()` وابسته است. اما `sanitize_callback` روی **هر** فراخوانی `update_post_meta` اجرا می‌شود — از جمله در **مهاجرت خودکار، کرون، WP-CLI و بازگردانی بازنگری** که در آن‌ها کاربر جاری وجود ندارد. نتیجه: `current_user_can` مقدار `false` برمی‌گرداند و کد PHP **بی‌صدا پاک می‌شد**.

مسخره اینجاست که مهاجرت خودکاری که خودم برای «حفظ داده» نوشتم، خودش داده را نابود می‌کرد.

#### ۳. کاربر کم‌دسترسی کد دیگران را پاک می‌کرد

در `Metabox::save()` مقدار پاک‌سازی‌شده (اغلب خالی) ذخیره می‌شد، حتی وقتی کاربر اصلاً اجازه ویرایش آن فیلد را نداشت.

### راه‌حل

`sanitize_callback` **کاملاً حذف شد**. پاک‌سازی جای درستش است: مرز ورودی فرم (`Metabox::save`) نه لایه ذخیره‌سازی.

| فیلد | قانون قبلی | قانون جدید |
|---|---|---|
| `_chs_js` | `raw_html` (مخرب) | `code` — دست‌نخورده |
| `_chs_php` | `raw_php` (پاک‌کننده) | `raw_php` — دیگر پاک نمی‌کند |
| `_chs_css` | `css` | `css` (بدون تغییر) |
| `_chs_html` | `raw_html` | `raw_html` (درست بود) |

و در `Metabox::save()`: اگر کاربر اجازه ندارد، فیلد **اصلاً به‌روزرسانی نمی‌شود** — به‌جای اینکه با مقدار خالی بازنویسی گردد.

امنیت حفظ شده: اجرای PHP همچنان به امضای HMAC مشروط است، و ذخیره JS/هدر/فوتر همچنان `unfiltered_html` می‌خواهد — فقط حالا به‌جای «مثله‌کردن کد»، تغییر را رد می‌کند.

## چرا CSS و JS اجرا نمی‌شدند؟

### علت: صف‌بندی در زمان اشتباه

ترتیب واقعی هوک‌های وردپرس:

```
wp_head    → wp_print_styles          اولویت ۸
           → Renderer::output_header  اولویت ۹۹   ← خیلی دیر!
wp_footer  → wp_print_footer_scripts  اولویت ۲۰
           → Renderer::output_footer  اولویت ۹۹   ← خیلی دیر!
           → delay_engine             اولویت ۹۹۹۹ ← خیلی دیر!
```

من `wp_enqueue_style()` و `wp_enqueue_script()` را داخل `output_header`/`output_footer` صدا می‌زدم — یعنی **بعد** از اینکه وردپرس استایل‌ها و اسکریپت‌ها را چاپ کرده بود. صف‌بندی در آن لحظه هیچ اثری ندارد؛ فایل ساخته می‌شد ولی هرگز در HTML نمی‌آمد.

بدتر: تابع `enqueue_snippet_js()` مقدار `true` برمی‌گرداند (یعنی «موفق شدم») و در نتیجه کد به حالت inline هم برنمی‌گشت. **CSS/JS سراسری کاملاً ناپدید می‌شد.**

همین مشکل برای موتور اجرای با تاخیر بود: روی `wp_footer` اولویت ۹۹۹۹ صف می‌شد، یعنی بعد از چاپ اسکریپت‌های فوتر. پس هر قطعه‌کدی که «اجرای با تاخیر» داشت، محتوایش داخل `<template>` می‌ماند و **هرگز اجرا نمی‌شد**.

### راه‌حل

1. **صف‌بندی به `wp_enqueue_scripts` منتقل شد** (متد جدید `enqueue_global_assets`) — زمان استانداردی که وردپرس برای این کار در نظر گرفته.
2. **موتور تاخیر از اولویت ۹۹۹۹ به ۵ آمد** تا قبل از چاپ اسکریپت‌های فوتر باشد.
3. **بازگشت امن (fallback):** اگر پنجره صف‌بندی گذشته باشد (مثلاً شورت‌کد وسط محتوا)، `enqueue_snippet_css/js` حالا `false` برمی‌گرداند و کد به‌صورت inline چاپ می‌شود. موتور تاخیر هم در این حالت مستقیماً inline چاپ می‌گردد.
4. **جلوگیری از تکرار:** اگر فایل صف شده، نسخه inline چاپ نمی‌شود.

### یک باگ دیگر که حین بررسی پیدا شد

`Assets::write()` بدون شرط `require_once ABSPATH . 'wp-admin/includes/file.php'` می‌کرد. در بافت فرانت‌اند این فایل در دسترس نیست و **خطای مرگبار** می‌داد. حالا بررسی `is_readable` انجام می‌شود و نوشتن فایل هم **اتمیک** شده (نوشتن در فایل موقت + `rename`) تا فایل نیمه‌کاره به مرورگر سرو نشود.

## ابزار بازیابی کدهای آسیب‌دیده

چون ممکن است کدهای شما از قبل ناقص ذخیره شده باشند، یک ابزار بازیابی اضافه کردم:

**قطعه کدهای من ← بازیابی کدهای ناقص**

این ابزار:
- بازنگری‌های وردپرس را می‌گردد و نسخه‌های سالم‌تر را پیدا می‌کند
- تشخیص می‌دهد کدام فیلد بریده شده (مقدار فعلی پیشوندِ نسخه قبلی است یا خالی شده)
- جدولی از آسیب‌ها با اندازه فعلی و اندازه قابل بازیابی نشان می‌دهد
- با یک کلیک همه را بازمی‌گرداند و کد PHP را دوباره امضا می‌کند
- در پیشخوان هشدار خودکار نمایش می‌دهد

⚠️ **اگر بازنگری برای قطعه‌کدی وجود نداشته باشد، بازیابی خودکار ممکن نیست.** در آن صورت باید کد را دستی وارد کنید.

## دستور کار پیشنهادی

1. **از دیتابیس نسخه پشتیبان بگیرید.**
2. نسخه `3.0.1` را نصب کنید.
3. به **قطعه کدهای من ← بازیابی کدهای ناقص** بروید و اگر موردی یافت شد، «بازیابی همه» را بزنید.
4. قطعه‌کدهایی که بازنگری نداشتند را چشمی بررسی کنید (به‌ویژه JS دارای `<`، `>` یا arrow function).
5. اگر PHP دارید: مطمئن شوید `define( 'CHS_DISABLE_PHP', false );` در `wp-config.php` هست و قطعه‌کدها را یک‌بار ذخیره کنید تا امضا بگیرند.

## درس معماری

اشتباه اصلی من این بود که پاک‌سازی را در **لایه ذخیره‌سازی** گذاشتم. `sanitize_callback` روی هر مسیر نوشتن اجرا می‌شود — مهاجرت، کرون، REST، WP-CLI، بازگردانی — و نمی‌تواند به `current_user_can` تکیه کند چون در بسیاری از آن بافت‌ها کاربری وجود ندارد.

پاک‌سازی باید در **مرز ورودی نامطمئن** (فرم HTTP) انجام شود، جایی که هم کاربر مشخص است و هم می‌دانیم داده از کجا آمده. همچنین هرگز نباید فیلتر HTML را روی کد برنامه‌نویسی اعمال کرد.

تست‌های قبلی من این را نگرفتند چون شبیه‌ساز وردپرسم `sanitize_callback` را اجرا نمی‌کرد — تست، مسیر واقعی کد را پوشش نمی‌داد. حالا ۲۲ تست رگرسیون اضافه کردم که دقیقاً همین هشت باگ را می‌سنجند.

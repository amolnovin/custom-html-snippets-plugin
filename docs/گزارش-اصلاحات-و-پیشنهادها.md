## بخش اول: مشکلات برطرف‌شده

### 🔴 امنیتی (بحرانی)

#### ۱. دو اکشن AJAX بدون nonce و بدون بررسی دسترسی
**مشکل:** `chs_search_posts` و `chs_get_page_titles` هیچ `check_ajax_referer` و هیچ `current_user_can` نداشتند. هر کاربر لاگین‌شده (حتی «مشترک») می‌توانست کل نوشته‌های سایت را جستجو کند و — چون `get_the_title()` بررسی دسترسی نمی‌کند — **عنوان پیش‌نویس‌ها و پست‌های خصوصی** را استخراج کند. همچنین در برابر CSRF باز بودند.

**اصلاح:**
```php
check_ajax_referer( 'chs_ajax_nonce', 'nonce' );
if ( ! current_user_can( chs_manage_cap() ) ) {
    wp_send_json_error( array( 'message' => '...' ), 403 );
}
```
به‌علاوه در `chs_ajax_get_page_titles` فقط پست‌های `publish` برگردانده می‌شوند، و سقف ۲۰۰ شناسه برای جلوگیری از DoS اعمال شد. نانس با `wp_json_encode` به جاوااسکریپت تزریق و به هر دو درخواست `$.post` اضافه شد.

#### ۲. `eval()` با بررسی دسترسی اشتباه
**مشکل:** شرط اجرا `chs_can_edit_php()` بود که `current_user_can('unfiltered_html')` را روی **بازدیدکننده** بررسی می‌کرد، نه نویسنده کد. نتیجه: کد PHP برای بازدیدکننده عادی هرگز اجرا نمی‌شد (باگ کارکردی) و در عین حال هر کسی که به دیتابیس دسترسی می‌یافت می‌توانست کد دلخواه تزریق کند.

**اصلاح:** سیستم امضای رمزنگاری‌شده:
```php
function chs_php_hash( $php ) {
    return hash_hmac( 'sha256', (string) $php, wp_salt( 'chs_php_exec' ) );
}
```
هنگام ذخیره، امضای HMAC کد + شناسه نویسنده ثبت می‌شود. هنگام اجرا، `chs_php_is_runnable()` بررسی می‌کند که امضا با کد فعلی مطابقت دارد (`hash_equals` برای جلوگیری از timing attack) و نویسنده هنوز `unfiltered_html` دارد. دستکاری مستقیم دیتابیس بدون دسترسی به `wp-config.php` بی‌اثر است.

#### ۳. پیش‌فرض ناامن `CHS_DISABLE_PHP`
**اصلاح:** پیش‌فرض از `false` به **`true`** تغییر کرد (امن به‌صورت پیش‌فرض). فعال‌سازی نیازمند افزودن آگاهانه `define( 'CHS_DISABLE_PHP', false );` در `wp-config.php` است. هشدار دائمی در پیشخوان هنگام فعال بودن اضافه شد.

#### ۴. XSS ذخیره‌شده از طریق نقش‌های کم‌دسترسی
**مشکل:** فیلدهای Header/HTML/JS/Footer بدون هیچ فیلتری ذخیره و در فرانت‌اند چاپ می‌شدند. CPT هم `capability_type` اختصاصی نداشت.

**اصلاح:** سه لایه:
- CPT حالا `capabilities` اختصاصی دارد (پیش‌فرض `manage_options`، با فیلتر `chs_manage_capability` قابل تغییر)
- ذخیره HTML/JS/Header/Footer خام نیازمند `unfiltered_html` است؛ در غیر این صورت فقط `wp_kses_post` روی HTML اعمال می‌شود
- `show_in_rest => false` تا کدها از REST API افشا نشوند

#### ۵. فرار از تگ `<style>` در فیلد CSS
**اصلاح:** تابع `chs_sanitize_css()` که `</style>`، `<script`، `javascript:` و `expression(` را حذف می‌کند.

#### ۶. ترتیب اشتباه بررسی امنیتی در `chs_toggle_active`
**اصلاح:** `check_admin_referer` **قبل از** بررسی مجوز منتقل شد و کد وضعیت HTTP صحیح (۴۰۰/۴۰۳) اضافه شد.

### 🟠 باگ‌های کارکردی

#### ۷. مخفی‌سازی محصول ووکامرس کاملاً بی‌اثر بود
**مشکل:** `chs_hide_woocommerce_product_elements()` از داخل `the_content` صدا زده می‌شد و روی `wp_head` هوک می‌کرد — ولی در آن لحظه `wp_head` **قبلاً اجرا شده بود**. یعنی نه استایل چاپ می‌شد و نه `remove_action`ها اثر داشتند.

**اصلاح:** بررسی `did_action('wp_head')`؛ اگر گذشته باشد استایل بی‌درنگ چاپ می‌شود، وگرنه روی هوک می‌رود. `remove_action`ها فوراً اجرا می‌شوند. محافظ `static $done` برای جلوگیری از تکرار اضافه شد.

#### ۸. افزودن فیلتر `the_content` در حین اجرای خودش
**مشکل:** در حالت `replace="true"` یک `add_filter('the_content', ...)` داخل خود اجرای `the_content` اضافه می‌شد که در همان درخواست بی‌اثر بود و به درخواست‌های بعدی نشت می‌کرد.

**اصلاح:** جایگزینی با الگوی پرچم وضعیت (`chs_mark_content_replaced()`) و اولویت‌گذاری صحیح فیلتر (`priority 20`).

#### ۹. مقایسه strict با نوع داده ناهمگون
**مشکل:** `in_array( $current_id, $excluded, true )` — اگر شناسه‌ها به‌صورت رشته ذخیره شده بودند (داده قدیمی)، مقایسه **بی‌صدا شکست می‌خورد** و قوانین استثنا اعمال نمی‌شد.

**اصلاح:** `array_map('intval', ...)` در هر دو getter و کست `(int)` روی `get_queried_object_id()`.

#### ۱۰. اجرا روی ذخیره خودکار و بازنگری‌ها
**اصلاح:** هوک به `save_post_custom_snippet` تغییر کرد و گاردهای `DOING_AUTOSAVE` / `wp_is_post_revision` / `wp_is_post_autosave` اضافه شد. (یک خط تکراری گارد هم حذف شد.)

#### ۱۱. بازگشت بی‌نهایت شورت‌کد
**اصلاح:** محافظ `static $rendering` — قطعه‌کدی که شورت‌کد خودش را صدا بزند باعث کرش نمی‌شود.

### 🟡 کارایی

#### ۱۲. ترنزینت چندمگابایتی (مهم‌ترین مشکل کارایی)
**مشکل:** کوئری `SELECT ... post_content ... LIMIT 500` کل محتوای ۵۰۰ نوشته را در یک ترنزینت (جدول `options`) ذخیره می‌کرد. روی سایت‌های محتوامحور این رکورد می‌توانست چند مگابایت شود و در هر درخواست بارگذاری گردد.

**اصلاح:** کش به‌ازای هر قطعه‌کد، `LIMIT 100`، و مهم‌تر: `unset( $candidate->post_content )` قبل از ذخیره در کش. همچنین `NOT IN` که با الحاق رشته ساخته می‌شد به **placeholderهای پارامتری `%s`** تبدیل شد.

#### ۱۳. مشکل N+1 در `chs_get_active_snippets_ids()`
**مشکل:** `posts_per_page => -1` سپس حلقه‌ای که برای هر قطعه‌کد یک `get_post_meta` جدا می‌زد.

**اصلاح:** فیلتر فعال‌بودن با `meta_query` به همان کوئری منتقل شد؛ سقف ۵۰۰، غیرفعال‌کردن `update_post_term_cache`.

#### ۱۴. نشت ترنزینت‌ها
**اصلاح:** `chs_flush_cache()` حالا ترنزینت‌های به‌ازای قطعه‌کد را با الگوی `LIKE` پیدا و پاک می‌کند و `wp_cache_delete` را هم صدا می‌زند.

## بخش دوم: پیشنهادهای حرفه‌ای برای ارتقای افزونه

### الف) معماری — مهم‌ترین گام بعدی

**۱. شکستن فایل تک‌تکه ۱۹۰۰ خطی.** ساختار پیشنهادی:
```
custom-html-snippets.php      ← فقط بوت‌استرپ و تعریف ثابت‌ها
includes/
  class-chs-plugin.php        ← ارکستراتور
  class-chs-post-type.php
  class-chs-metabox.php
  class-chs-renderer.php
  class-chs-cache.php
  class-chs-security.php
  class-chs-ajax.php
assets/
  css/admin.css               ← به‌جای ۵۰۰ خط CSS داخل wp_add_inline_style
  js/admin.js                 ← به‌جای رشته‌های جاوااسکریپت داخل PHP
```
CSS و JS جدا شدنی‌اند و آنگاه از کش مرورگر و minify بهره می‌برند. رشته‌های JS داخل PHP هم خطاخیزند و ادیتور از آن‌ها پشتیبانی نمی‌کند.

**۲. فضای نام (namespace) و بارگذاری خودکار.** پیشوند `chs_` روی ۴۸ تابع سراسری ریسک تداخل دارد. `namespace AmolNovin\CHS;` + autoloader مبتنی بر Composer.

**۳. استفاده از `register_post_meta()`** با `show_in_rest => false`، `single => true` و `sanitize_callback` — به‌جای `update_post_meta` دستی. پاک‌سازی متمرکز و قابل اتکا می‌شود.

### ب) امنیت — سطح بعدی

**۴. حالت «کد امن» (Safe Mode).** اگر قطعه‌کدی خطای مرگبار داد، در بارگذاری بعدی خودکار غیرفعال شود. پیاده‌سازی: قبل از `eval` یک option با شناسه قطعه‌کد بنویسید، بعد از موفقیت پاکش کنید. اگر هنگام بوت آن option موجود بود یعنی دفعه قبل کرش کرده → غیرفعال کن. (این دقیقاً کاری است که افزونه Code Snippets انجام می‌دهد و «سایت سفید» را از بین می‌برد.)

**۵. اعتبارسنجی نگارشی قبل از ذخیره.** با `php -l` روی فایل موقت یا `token_get_all()` در بلوک `try`، خطای نگارشی را **پیش از** ذخیره بگیرید.

**۶. لاگ حسابرسی (Audit Log).** چه کسی، چه زمانی، کدام قطعه‌کد را تغییر داد. برای سایت‌های چندکاربره ضروری است. با `post_meta` یا جدول اختصاصی.

**۷. Content Security Policy.** برای اسکریپت‌های اینلاین، پشتیبانی از `nonce` در CSP اضافه کنید تا با سایت‌های سخت‌گیرانه سازگار باشد.

### ج) کارایی

**۸. جایگزینی `the_content` با هوک‌های قالب.** فیلتر `the_content` روی هر پست در آرشیوها هم اجرا می‌شود. برای تزریق، هوک‌های `wp_body_open`، `loop_start` یا موقعیت‌های سفارشی دقیق‌تر و سبک‌ترند.

**۹. تحویل CSS/JS به‌صورت فایل به‌جای اینلاین.** برای قطعه‌کدهای سراسری، فایل فیزیکی در `wp-content/uploads/chs/` بسازید و با `wp_enqueue_script/style` و پارامتر نسخه (hash محتوا) صف کنید. مزایا: کش مرورگر، پشتیبانی HTTP/2، حذف حجم از HTML، سازگاری با افزونه‌های بهینه‌سازی.

**۱۰. پشتیبانی از کش آبجکت پایدار.** `wp_cache_*` را با گروه `chs_plugin` به‌صورت `wp_cache_add_global_groups` ثبت کنید تا روی Redis/Memcached درست کار کند.

**۱۱. بارگذاری تنبل (Lazy) پیشرفته.** موتور فعلی خوب است؛ گزینه `IntersectionObserver` را هم اضافه کنید تا قطعه‌کد فقط هنگام ورود به دید کاربر اجرا شود (بهتر برای LCP).

### د) تجربه کاربری و قابلیت‌ها

**۱۲. درون‌ریزی/برون‌بری (Import/Export) JSON.** انتقال قطعه‌کدها بین محیط staging و production. تقریباً اولین چیزی است که کاربران حرفه‌ای می‌خواهند.

**۱۳. شرط‌های نمایش پیشرفته‌تر.** فعلاً فقط لیست صفحات است. اضافه کنید:
- بر اساس نوع محتوا، دسته، برچسب، تمپلیت
- بر اساس نقش کاربر / لاگین‌بودن
- بر اساس دستگاه (موبایل/دسکتاپ)
- بازه زمانی (شروع/پایان انتشار) — برای کمپین‌ها عالی است
- بر اساس پارامتر URL یا کوکی (برای A/B تست)

**۱۴. بازنگری و بازگردانی (Revisions).** پشتیبانی `revisions` را در CPT فعال کردم، ولی متاها در بازنگری ذخیره نمی‌شوند. با هوک‌های `_wp_put_post_revision` و `wp_restore_post_revision` متاها را هم نسخه‌بندی کنید. برای کدنویسی، «برگرد به نسخه قبل» ارزش زیادی دارد.

**۱۵. کپی‌کردن قطعه‌کد (Duplicate)** و **دسته‌بندی/برچسب** برای مدیریت ده‌ها قطعه‌کد.

**۱۶. جستجوی داخل کد قطعه‌کدها** در لیست پیشخوان — وقتی ۵۰ قطعه‌کد دارید حیاتی است.

**۱۷. بلوک گوتنبرگ + ویجت المنتور.** بسیاری از کاربران هرگز شورت‌کد تایپ نمی‌کنند. یک بلوک با انتخابگر کشویی قطعه‌کد و پیش‌نمایش زنده، پذیرش افزونه را چند برابر می‌کند.

**۱۸. پیش‌نمایش زنده.** یک iframe در صفحه ویرایش که HTML/CSS/JS را بی‌درنگ رندر کند.

### هـ) کیفیت و نگهداری

**۱۹. WordPress Coding Standards.** اجرای `phpcs` با استاندارد `WordPress` و `WordPress-VIP-Go`:
```bash
composer require --dev wp-coding-standards/wpcs phpcompatibility/phpcompatibility-wp
phpcs --standard=WordPress custom-html-snippets.php
```

**۲۰. تست خودکار.** من یک هارنس تست (`tests/`) با ۴۲ تست ساختم که بدون نصب وردپرس اجرا می‌شود. گام بعدی: `PHPUnit` + `WP_UnitTestCase` و اجرای آن در GitHub Actions روی PHP 7.4 تا 8.3.

**۲۱. `readme.txt` استاندارد مخزن وردپرس** با `Stable tag`، `Tested up to`، `Changelog` و بخش FAQ.

**۲۲. مسیر ارتقای داده (Migration).** با `chs_version` که اضافه کردم، هنگام تغییر ساختار متا در نسخه‌های بعدی می‌توانید مهاجرت خودکار بنویسید. **نکته مهم:** برای کاربرانی که از ۲.۳ به ۲.۴ می‌آیند و از PHP استفاده می‌کردند، کدها امضا ندارند و اجرا نمی‌شوند — باید یک‌بار قطعه‌کد را باز و ذخیره کنند (یا یک روتین مهاجرت بنویسید که برای کدهای موجود امضا بسازد).

## نکات مهم هنگام به‌روزرسانی

1. **قبل از هر چیز از دیتابیس نسخه پشتیبان بگیرید.**
2. اگر از قابلیت PHP استفاده می‌کردید: چون پیش‌فرض حالا امن است، باید `define( 'CHS_DISABLE_PHP', false );` را به `wp-config.php` اضافه کنید، سپس هر قطعه‌کد PHP را یک‌بار **باز و ذخیره** کنید تا امضای امنیتی ساخته شود.
3. دسترسی مدیریت قطعه‌کدها اکنون `manage_options` است. برای دادن دسترسی به نقش دیگر:
   ```php
   add_filter( 'chs_manage_capability', fn() => 'edit_pages' );
   ```
4. کاربرانی که `unfiltered_html` ندارند دیگر نمی‌توانند JS خام ذخیره کنند — این عمدی و برای جلوگیری از XSS است.
